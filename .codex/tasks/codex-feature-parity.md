# Codex feature parity

Status: in progress. Objective: match Codex desktop workflows supported by Codex CLI and app-server without requiring users to install the CLI package for normal work. The active goal authorizes version changes and release publication after validation.

Official baseline: [Codex app overview](https://openai.com/index/introducing-the-codex-app/) documents isolated worktrees, review/comment workflows, skills, and scheduled automations. [OpenAI's App Server architecture](https://openai.com/index/unlocking-the-codex-harness/) describes the shared harness and the client protocol for persistent threads, turns, tool events, approvals, and review.

Completed and published on `main`: pre-window update check and install (`0.0.010`); per-chat managed worktrees.

Current branch: `codex/app-parity-thread-fork`. Thread context-menu forks use app-server `thread/fork`; a real saved session was forked into a temporary Git worktree using its `cwd` override, then both test artifacts were cleaned. Review uses app-server `review/start`; its full review turn still needs end-to-end verification. The branch also includes per-file diff viewing and selected diff context in the prompt.

Version is `0.0.022`. Normal turns, review, thread history, model discovery, ChatGPT device-code sign-in, worktree forks, scheduled automations with optional existing-thread continuation, interactive App Server requests, multi-agent browsing, and terminal tabs use the standalone official App Server runtime `0.163.0`, downloaded and SHA-256 verified on first launch. Automation definitions and run review records persist in LocalAppData; a 30-second local scheduler runs while CodexGUI is open, and launched turns use the detached worker. Unattended runs use `approvalPolicy=never` with `workspaceWrite` and sandbox network disabled; configured MCP integrations remain available. Git worktree isolation is enabled by default. Diff review has syntax-colored lines and line-anchored comment threads with local replies, which can be attached to chat context. Existing verification through `0.0.020` is recorded in Git history. For `0.0.021`, `dotnet build --no-restore` passes with zero warnings and errors; a harmless PowerShell command/exec PTY request passed, and the terminal host launched a shell, sent stdin, and terminated it via App Server. On Windows, sandboxed streamed PTY sessions fail, so the UI requires explicit per-window consent before starting a full-access terminal unless project Full Access is already enabled. Multi-agent receiver/status parsing remains reflection-tested. Interactive request payload serialization and App Server capability initialization were checked for `0.0.018`; live MCP elicitation and scheduled automation runs remain untested. Terminal tab keyboard/output behavior and full-screen TUI rendering have not been exercised in the running GUI. Visual review/diff layout, full `review/start`, UI-driven approval/steer/interrupt, and device-code login remain unverified. For `0.0.022`, `dotnet build --no-restore` passes with zero warnings and errors, and `git diff --check` is clean. The full scheduled-run UI path was not exercised; a no-turn `thread/start` smoke session cannot be resumed because it has no persisted rollout, so existing-thread continuation still needs an end-to-end run against a real saved conversation. CLI is still used for plugin marketplace management and recovery of pre-`0.0.015` runs. The standalone App Server binary is pinned to the client; the generic CLI `app-server` command is labeled experimental by upstream docs.

Known gaps: full-screen terminal emulation and plugin marketplace management without CLI. Keep interim work on a feature branch; publish the verified final release to `main` when parity is ready.
